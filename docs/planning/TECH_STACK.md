## 2. Frontend web y móvil

### 2.1 Alternativas evaluadas

| Opción                                                   | A favor                                                                                                                                                                                                                                                 | En contra                                                                                                                                    | Veredicto                                                                                          |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| **A. Expo universal (Expo Router: iOS + Android + Web)** | Un solo código de pantallas, navegación y lógica · rutas por archivos iguales en todas las plataformas · Expo Router genera web estática (SEO para la biblioteca pública) · EAS Build · archivos `.web.tsx` y `.native.tsx` para adaptar por plataforma | La web hecha con react-native-web es menos flexible que el DOM puro (tablas complejas, editores) · algunas librerías web no sirven en nativo | **Elegida**                                                                                        |
| B. Next.js (web) + Expo (móvil) con paquetes compartidos | La mejor web posible (SSR y ecosistema) · panel de administración más cómodo                                                                                                                                                                            | **Duplica las pantallas**: cada recorrido se escribe dos veces · en una semana no alcanza para las dos plataformas completas                 | Descartada para esta etapa. Se reconsidera si el panel de administración crece mucho (ver ADR-004) |
| C. React + Vite (web) + Capacitor (móvil)                | Web excelente · un código                                                                                                                                                                                                                               | La experiencia móvil es una webview · peor acceso a funciones nativas y navegación menos natural                                             | Descartada                                                                                         |
| D. Flutter                                               | Buena experiencia multiplataforma                                                                                                                                                                                                                       | Otro lenguaje (Dart) · no comparte tipos ni validaciones con un backend TypeScript · la web de Flutter es pobre para contenido indexable     | Descartada                                                                                         |

**Cómo se mitiga la limitación de la opción A en el panel de administración.** Las vistas de administración se diseñan primero para la web (tablas con `FlatList` y columnas adaptables) y en el móvil se muestran como listas. Si un componente necesita el DOM (por ejemplo, un editor de Markdown enriquecido), se implementa en `Component.web.tsx`, y en nativo se ofrece una versión simplificada o "disponible en la web".

## 3. Backend

### 3.1 Alternativas evaluadas

| Opción                                                         | A favor                                                                                                                                                                                                                                          | En contra                                                                                                                                                                                         | Veredicto                                            |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **Supabase (datos, Auth, RLS, RPC) + API propia en Hono/Node** | La autorización vive en la base (RLS), así que no depende del frontend · la API concentra los secretos, la IA, la puntuación y los procesos · Hono funciona en Node, Vercel, Deno y Bun, sin quedar atado a un proveedor · TypeScript compartido | Dos capas de servidor que hay que entender (se documenta qué va en cada una)                                                                                                                      | **Elegida**                                          |
| Solo Supabase (PostgREST + Edge Functions en Deno)             | Un solo proveedor                                                                                                                                                                                                                                | Deno con el monorepo de pnpm complica compartir paquetes · límites de tiempo de las Edge Functions para el streaming de la IA **[A verificar]** · menos práctica con Node, que pide la evaluación | Descartada como API principal                        |
| NestJS + Prisma o Drizzle, con autenticación propia            | Arquitectura muy estructurada                                                                                                                                                                                                                    | Mucho código de base · duplica la autorización (RLS + guards) · Prisma no gestiona políticas RLS                                                                                                  | Descartada (complejidad sin beneficio en una semana) |
| Express                                                        | Muy conocido                                                                                                                                                                                                                                     | Sin tipos de punta a punta ni validación integrada; API más antigua                                                                                                                               | Descartada en favor de Hono                          |

### 3.2 Regla de las tres vías

Esta regla define dónde va cada operación:

1. **Cliente → PostgREST (Supabase) con RLS:** lecturas y escrituras simples sobre filas propias (por ejemplo, editar el perfil o guardar un favorito).
2. **Cliente → RPC (función PL/pgSQL):** operaciones **atómicas** sobre varias tablas que no necesitan secretos ni servicios externos (por ejemplo, crear una familia junto con la membresía de su dueño, o aceptar una asignación con sus permisos).
3. **Cliente → API Hono:** todo lo que necesite **secretos, servicios externos, lógica compleja en TypeScript o escrituras privilegiadas**: IA, puntuación de evaluaciones, ingestión de documentos, envío de correos, exportación y borrado de cuentas, verificación de credenciales y reinicio de la demo.

El detalle está en `ARCHITECTURE.md`.

## 4. Base de datos

| Criterio                                                      | PostgreSQL (Supabase)                                                                                                                                                                          | MySQL (PlanetScale, Aiven)                                           | MongoDB o Firebase                      |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- | --------------------------------------- |
| Relaciones muchos-a-muchos complejas e integridad referencial | Excelente                                                                                                                                                                                      | Buena                                                                | Débil: documentos sin claves foráneas   |
| Seguridad por fila                                            | **RLS nativo**                                                                                                                                                                                 | No tiene RLS nativo: todo en la aplicación                           | Firestore tiene reglas, pero no son SQL |
| Búsqueda vectorial para RAG                                   | `pgvector` en la misma base                                                                                                                                                                    | Requiere otro servicio o soporte reciente limitado **[A verificar]** | Atlas Vector Search (otro proveedor)    |
| Búsqueda de texto completo en español                         | `tsvector` con la configuración `spanish`                                                                                                                                                      | FULLTEXT, más limitado                                               | Limitada                                |
| Transacciones                                                 | ACID completas y funciones PL/pgSQL                                                                                                                                                            | ACID                                                                 | Limitadas                               |
| Migraciones                                                   | Supabase CLI (SQL versionado)                                                                                                                                                                  | Herramientas externas                                                | Sin esquema                             |
| Costo inicial                                                 | Plan gratuito de Supabase: 500 MB, 50.000 usuarios activos por mes, 1 GB de archivos, **se pausa tras 7 días sin actividad y no tiene backups** (según la investigación §20) **[A verificar]** | Variable                                                             | Plan gratuito                           |

**Decisión: PostgreSQL en Supabase.** No es por popularidad: el modelo es intensamente relacional (familias, integrantes, profesionales, permisos por alcance), la autorización tiene que vivir cerca de los datos (RLS) y el RAG necesita búsqueda vectorial e híbrida. Las tres cosas quedan en un solo motor y un solo respaldo.

**Región:** São Paulo (`sa-east-1`), la más cercana a Argentina. Implica una transferencia internacional de datos que tiene que evaluar un abogado (ver `SECURITY_AND_PRIVACY.md`).

## 5. Autenticación y almacenamiento

**Supabase Auth** cubre el registro con correo, la verificación de correo, la recuperación de contraseña, OAuth con Google y GitHub, la renovación de sesiones (JWT de corta duración + refresh token rotativo) y MFA con TOTP para administradores.

**Qué queda en Supabase y qué en el backend propio:**

| Responsabilidad                              | Supabase                              | API propia                                                                          |
| -------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------- |
| Identidad, contraseñas, OAuth, sesiones, MFA | ✅                                    | —                                                                                   |
| Emisión del JWT                              | ✅                                    | Lo **valida** en cada pedido (JWKS o secreto)                                       |
| Autorización sobre los datos                 | ✅ RLS y funciones `has_permission()` | Verificaciones adicionales antes de operar con privilegios                          |
| Archivos                                     | ✅ Storage con políticas              | Genera URLs firmadas de corta duración cuando el acceso depende de reglas complejas |
| Correos de autenticación                     | ✅ (con SMTP de Resend)               | Correos de invitación y notificaciones                                              |

**Tercer proveedor de identidad.** Se evaluó **Sign in with Apple**. Las pautas de revisión de la App Store exigen ofrecer una opción de inicio de sesión equivalente y respetuosa de la privacidad cuando la app usa proveedores de terceros como Google (pauta 4.8) **[A verificar la redacción vigente]**. Por eso **solo aporta valor real si se publica en iOS**, lo que además requiere el Apple Developer Program (US$99 por año) **[A verificar]**. Queda en P2, junto con la publicación en iOS. Microsoft y Facebook no aportan valor para este público.

**Correo:** Supabase recomienda configurar un SMTP propio para producción porque el incluido tiene un límite bajo de envíos **[A verificar]**. Se usa Resend (plan gratuito) con un dominio verificado.

### 6.2 Embeddings

Para los embeddings se elige **Voyage AI**, el proveedor recomendado en la documentación de Anthropic, con un modelo multilingüe. La alternativa es OpenAI `text-embedding-3-small`.

**La dimensión se fija en 1024**, porque ambos modelos permiten reducir la salida a ese tamaño **[A verificar el modelo vigente y sus dimensiones]**. Cambiar de modelo implica reindexar, y está previsto: `kb_chunks` guarda `embedding_model`.
